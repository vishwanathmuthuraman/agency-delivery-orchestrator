Agency Delivery Orchestrator

Status: documentation blueprint and original synthetic examples. The application is not implemented. No completed benchmark, customer deployment, autonomous production capability or time saving is claimed. Expected-result files describe intended behavior, not measured output.

A planned local simulator for coordinating an agency campaign from an approved brief to verified delivery. It models the work around creative production: collecting inputs, planning tasks and capacity, arranging handoffs, gathering feedback, handling changes, checking approvals and preparing a billing evidence packet.

The most detailed demonstration asks: when a client changes a fact, requirement or deadline, can we identify the affected work, make its consequences clear, obtain the right decisions, and verify that the correction was completed? That demonstration is one part of the full delivery lifecycle.

A concrete example

A fictional client approves a campaign containing a script, a video editing task, a caption and a scheduled social post. The client then changes an approved product claim. The proposed system identifies dependent outputs, pauses affected dispatches, estimates additional work using versioned rates, and presents a commercial choice. After an authorized decision, it drafts a supported caption correction, prepares a work packet for the human editor, requests approval of the new versions, and verifies the mock destination contains the approved version. Unrelated work continues.

The system must never turn “I sent a request” into “the work is finished.” A timeout means the result is unknown until the destination is reconciled. Changing a caption does not mean the spoken words inside a video have been changed.

The whole product scope

Delivery stage Planned v1 behavior
Brief and scope Validate a structured synthetic brief, deliverables, acceptance criteria and missing inputs.
Plan and budget Propose a task graph; calculate cost and capacity from explicit inputs; preserve an approved baseline.
Collect and coordinate Track input requests, task owners, blockers, handoffs and mock reminders.
Produce and review Route versioned work; prepare text drafts and human editing packets; collect role-specific decisions.
Manage changes Trace affected content, compare options and require approval of commercial consequences.
Complete delivery Recheck readiness, use a mock connector, reconcile uncertain results and verify observed versions.
Close the campaign Produce acceptance and delivery evidence plus a draft billing-readiness export.

This is a bounded agency workflow prototype. It is not a general ledger, tax engine, payroll system, purchasing suite, real publishing integration or a guarantee that every creative task can be automated. Future connections to those systems require separate scope and authorization.

Intended implementation

Python 3.12, SQLite, a deterministic command-line runner and a local HTML report. Default execution must work without credentials, network access or a model provider. An optional model adapter can propose dependency links, classifications and text revisions. Deterministic rules and explicit reviewer decisions remain responsible for authorization, money and state changes. An optional UI follows the working core.

The build plan contains future interface contracts, not a runnable installation guide. No product CLI or application package is claimed to exist today. Any documentation/schema validation scripts supplied with the blueprint validate only the specification artifacts.

01 — Product requirements

Specification version 0.1. All application requirements below are proposed and unachieved. The repository is a build blueprint. The user-facing promise of the eventual demonstration is: “Show what needs doing, why it matters, who must decide, and whether the accepted work actually reached the intended destination.”

1. Users and the job

The primary user is an agency delivery or account lead coordinating creative production. Other simulated roles are a producer, editor, client reviewer, commercial approver and release approver. A person may hold several roles, but a fixture must state each permission explicitly. The model is not a person with inherited authority.

The unit of work is a campaign containing deliverables, tasks, source facts, approvals and a commercial baseline. A deliverable might be a script, caption, editing package or simulated social post. A task is an action needed to produce or review it. A source fact is a versioned statement such as an approved product claim, launch date or required disclaimer. Keep these distinct: completing a task does not automatically accept a deliverable.

The public prototype must use fictional parties and records. A future discovery exercise can test the hypothesis with authorized examples, but an interview, customer, saving or deployment must never be implied by a synthetic scenario.

2. Full lifecycle and release boundaries

All v1 paths operate in local simulated time. No actual messages or posts leave the machine. There is no requirement to generate a finished video, change audio, infer legal approval, or operate every business department. The full lifecycle supplies context; selective change handling and verified closure receive the deepest implementation and evaluation.

3. Numbered functional requirements

Each acceptance criterion is a future behavior to verify, not a completed test.

ID Requirement Acceptance criterion
FR-01 Validate scenario and campaign contracts Reject invalid types, unresolved references, duplicate conflicting IDs, unsupported currency and invalid version progression before partial state is committed.
FR-02 Isolate clients Every read, mutation, model context and export is scoped to a tenant. A foreign reference produces a denial with no foreign content in errors or reports.
FR-03 Preserve the approved scope Store an immutable baseline of deliverables, acceptance criteria, schedule assumptions, rate versions and budget. Later changes create explicit revisions.
FR-04 Identify missing inputs Required but absent client material blocks only dependent tasks. An input receipt identifies its exact version and releases only eligible work.
FR-05 Plan work and capacity Validate an acyclic task graph, owners and estimates. Detect overallocated simulated capacity without silently moving a contractual deadline.
FR-06 Calculate money deterministically Use one currency per campaign, integer minor units, integer minutes and a documented rounding policy. Estimated, approved, committed and actual amounts remain separate.
FR-07 Coordinate work transparently Produce owner-specific next actions and simulated reminder/escalation events. Respect configured working windows, maximum reminder count and acknowledgement status.
FR-08 Preserve content lineage Store immutable deliverable revisions and explicit dependency links to source and upstream content revisions. A proposed link records evidence and review status.
FR-09 Distinguish proposals from facts Model-proposed dependencies, classifications, estimates and patches remain proposals until schema checks and applicable review pass. Unsupported claims cause abstention or rejection.
FR-10 Detect meaningful changes Ingest a new source or deliverable revision, identify affected current work, show supporting paths and leave unrelated work eligible. Missing or ambiguous evidence enters review.
FR-11 Offer commercial choices Present absorb, additional-fee, substitution or deadline-change options with explicit costs and assumptions. None becomes an agreed commercial commitment without an authorized decision.
FR-12 Prepare bounded corrective work Apply supported text replacements only to their stated base revision; produce human editing packets for unsupported media changes. Both remain drafts.
FR-13 Bind and invalidate approvals Bind each decision to purpose, actor, target revision, relevant source revisions and policy version. A relevant change prevents old approval from authorizing dispatch.
FR-14 Enforce scheduling readiness Require completed prerequisites, accepted current content, current commercial decision when needed, valid release authorization and a supported destination. Readiness is checked again at dispatch.
FR-15 Dispatch idempotently within the supported boundary A repeated intent/payload has at most one mock external effect. Reuse with changed payload is a conflict. New content revisions require new intent and authorization.
FR-16 Reconcile unknown outcomes After a response is lost, preserve an unknown state, query the mock destination by stable intent, and never blindly retry an action that might have completed.
FR-17 Verify delivery and closure Compare observed destination identity/version or content digest with the approved target. A request receipt alone cannot establish verified completion.
FR-18 Export billing readiness Produce a local draft packet containing accepted scope, authorized changes and verified delivery references. It must not create an invoice or imply payment.
FR-19 Make runs reproducible and inspectable Replaying the same fixture/configuration yields the same normalized state and decisions. The report exposes evidence, uncertainty and failure reasons.
FR-20 Evaluate without hidden-label leakage Strategies see the same observed facts and shared guard; future events and expected labels stay evaluator-only. Report failures, denominators and limitations.

4. Quality and safety requirements

NFR-01: the default simulator runs without network access or a provider key. NFR-02: state changes are durable across restart, with atomic local transactions and a migration version. NFR-03: narrative input, imported files and retrieved text are untrusted data, never tool instructions. NFR-04: logs avoid secrets and unnecessary client content; report rendering escapes untrusted strings. NFR-05: clock, role policy, reminder limits and connector behavior are injectable for tests. NFR-06: missing authority, ambiguous destination state and unsupported transformations produce explicit non-success states.

The application may transparently coordinate routine work under a configured policy. It must not impersonate a human, pressure staff, infer private psychological traits or promise a deadline, price or scope concession on behalf of a client or agency.

5. Required demonstration stories

These are intended v1 demonstration behaviors. The six supplied fixture files are narrower control specifications; they do not yet exercise all input, capacity, reminder and handoff behavior end to end. Build a separate full-lifecycle integration scenario before claiming the whole lifecycle works. Reviewed impacts and prepared revisions supplied as fixture events are simulated human inputs, not discoveries made by an implemented model.

  1. Clean delivery: approved scope progresses through input collection, text drafting, human production, review, mock delivery and billing readiness.
  2. Client claim changes: identify dependent caption and editing work, protect the old approved destination, approve a cost choice, correct and reapprove new revisions, then verify them.
  3. Stale approval: a source changes between preflight and dispatch. The final guard rejects old authorization even if the queue has not refreshed.
  4. Duplicate dispatch: repeated delivery and restart do not create a second effect; changed-payload key reuse fails visibly.
  5. Uncertain dispatch: a write attempt has no confirmed outcome. The public example remains in reconciliation rather than blindly retrying; a separate future recovery test finds an existing effect without creating another.
  6. Cross-client reference: a malicious brief points at another tenant's content or requests secret context. Retrieval and report generation deny it without disclosure.

These public stories teach the contract. Additional evaluation cases must vary structure and causes, not merely names.

An optional client request and a verified factual invalidation have different effects. A rejected optional request leaves the accepted baseline unchanged. A factual invalidation recorded by an authenticated trusted source owner immediately holds affected content independent of commercial negotiations; correction, current-source review and fresh approvals are required before dispatch resumes. The latter behavior requires an additional event contract during implementation.

6. Success, limits and non-goals

A successful v1 demonstrates the supported lifecycle faithfully, including useful work that can continue and work that needs a human. It does not achieve success by blocking everything, approving everything, or relabeling incomplete work as complete. Performance targets and safety gates are separated in definition of done.

Customer value remains a hypothesis: fewer forgotten consequences, clearer commercial choices and more reliable closure. Synthetic replay cannot establish hours saved, willingness to pay, operating margin improvement, industry-wide demand, legal compliance or competitive advantage. The source document deliberately records existing products with overlapping functionality.

02 — Architecture and behavioral contracts

Proposed architecture; application modules do not exist yet. JSON schemas in schemas/ are the field-level contracts. The semantics below govern implementation; if a fixture and this document disagree, resolve and record the conflict before coding rather than silently choosing one.

1. Bounded design

Use Python 3.12, SQLite, a CLI and a local report. Keep one package with explicit modules before introducing services. Suggested future directories are domain/, storage/, planning/, changes/, execution/, connectors/, agents/, replay/, evaluation/ and reports/. These are proposed paths, not present modules.

The runtime flow is: validate input → append observed event → materialize state → identify eligible work or review → calculate a proposed action → authorize exact versions → perform final dispatch checks → invoke the supported connector → reconcile and verify. The reporting layer reads evidence; it must not invent new state.

Default operation is offline. A deterministic mock model can demonstrate proposed extraction without claiming model intelligence. The optional model interface returns structured proposals only. A future UI consumes the same application services; duplicating money or authorization logic in a UI is prohibited.

2. Domain records and identifiers

Record Meaning and required semantics
Tenant and campaign Every campaign belongs to exactly one tenant. All queries use both identities; a guessed record ID cannot escape that boundary.
Commercial baseline Immutable accepted scope, deliverable list, schedule assumptions, budget and rate references. A baseline revision needs an authorized commercial decision.
Source fact Stable fact identity plus monotonically increasing immutable revision, value, origin and observed time. Examples include product claim or disclaimer.
Deliverable Stable identity and kind with immutable content revisions, acceptance criteria and intended destinations. Status alone does not identify content.
Dependency A typed edge from source/upstream content to downstream deliverable or task, with cited evidence, scope and review status. Direction means upstream change may affect downstream work.
Task Owner, prerequisites, required inputs, estimated minutes, explicit output and state. Task completion supplies evidence but cannot automatically grant client approval.
Approval Actor, purpose, decision, target identity/revision, relevant source revisions, policy version, observation time and optional expiry. Revocation is append-only.
Change case Triggering revision, affected paths, uncertainty, proposed work, commercial alternatives and resolution history. Separate from a task or final deliverable.
Action intent Stable logical action identity, immutable payload digest, target revision, authorization references and connector destination.
Receipt and observation Attempt outcome plus independently obtained destination state. Request acceptance and verified content are distinct facts.
Audit event Actor or system component, tenant/campaign, event identity, type, observed time, evidence references and resulting transition.

Use opaque string IDs. Do not encode secrets, customer names or hidden evaluation labels into IDs. Enforce composite uniqueness or tenant-qualified foreign keys. Refuse cross-tenant references before fetching referenced content, including evidence snippets and error messages. Tenant-aware cache keys include tenant, input digest, model/configuration and schema version.

3. State machines

State names here are behavioral concepts; map concrete enum names to the published schemas when implementing.

Campaign: draft → baseline_review → active → closure_review → closed. It can enter paused or cancelled from appropriate active states. Reopening a closed campaign requires a recorded reason and new review; it cannot erase the prior closure packet. Closed means the defined scope is resolved and evidence assembled, not that an invoice is paid.

Task: blocked → ready → in_progress → awaiting_review → completed. Review rejection returns work to ready with a new revision request. Cancelled is explicit. A stale output can create new corrective work; do not rewrite history to imply the original task never completed. Only the dependency and input rules determine readiness.

Deliverable revision: draft → in_review → accepted → dispatch_ready → verification_pending → verified. Rejected or superseded revisions remain in history. A change can remove current eligibility even when the old content bytes are unchanged. Already delivered content opens a correction case; it is not magically undone.

Approval: proposed decision → granted or denied; a grant may become expired, revoked or invalidated. Commercial, creative and release purposes are different. Client creative acceptance cannot grant an extra fee, and commercial approval cannot approve a new creative revision.

Change case: detected → impact_review → decision_required → authorized → correcting → reapproval → verification → resolved. It may instead close as no_change_required with a reason and evidence. Missing knowledge remains needs_information. A material ambiguity cannot be silently treated as no impact.

Action: proposed → authorized → queued → attempting → succeeded_unverified → verified. An explicit pre-effect rejection can become failed_safe. A lost response or ambiguous error becomes outcome_unknown → reconciling. Reconciliation may establish verified, succeeded_unverified, confirmed_no_effect or manual_resolution. Only confirmed_no_effect plus still-valid authorization permits a safe retry under the connector contract.

4. Revisions and approval validity

Never overwrite an accepted content revision or source value. A new source revision changes the known basis for downstream decisions. Relevant current approvals become ineligible until reviewed; this includes unchanged assets whose supporting fact changed. Materiality classification may propose that a change is benign, but v1 requires a recorded reviewer decision to retain eligibility after a cited source revision changes. Such a decision is a fresh approval referencing current sources, not a mutation of the old one.

At final dispatch, check tenant and actor authority, target content revision/digest, current relevant source revisions, policy version, expiry, required commercial decision, prerequisites and destination support. Recheck inside the local transaction that reserves the action. If any binding has changed, record the reason and hold. A previous green preflight is advisory.

Creative text, scope, price and destination are part of the authorized payload. A changed payload needs a new revision and intent. Approval for caption v2 cannot authorize caption v3 even when a model calls the edit minor. A reviewer decision must identify exactly what was displayed; an ambiguous “looks good” cannot be promoted automatically into all approval purposes.

5. Dependency and change analysis

Start with explicit synthetic edges. Validate endpoints and reject dependency cycles where they violate the task/deliverable graph contract. Calculate affected descendants deterministically. Every affected result includes at least one source-to-output path so a reviewer can inspect the reasoning. Include both pending and previously delivered outputs, while distinguishing their consequences.

An optional model can propose edges from bounded content excerpts. Each proposal states endpoints, relation, source citation and uncertainty. Check that quoted spans resolve to authorized observed content. Human review accepts or rejects proposed edges before they influence automatic eligibility. The system may surface uncertain candidates for review; it must not silently omit them to improve precision.

The graph cannot reveal an uncaptured dependency or an unknown external fact. The report must expose missing inputs, unreviewed links and unsupported media content. Treat a confidence score as a model estimate, not a probability validated by this project.

6. Money, estimates and capacity

Each campaign uses one explicit supported currency with a declared minor-unit exponent; v1 can restrict this to currencies with two decimal places. Store all amounts as bounded non-negative integers. Store effort as integer minutes and rates as integer minor units per hour, with immutable rate identity and revision. Round each task's minutes * minor_per_hour / 60 half-up to an integer minor unit, then sum rounded tasks. For non-negative integer inputs the calculation is (minutes * minor_per_hour + 30) // 60. This rounding policy must appear in exported explanations. Never mix float arithmetic, currency conversion or inconsistent rounding stages.

Preserve original baseline, approved changes, outstanding commitments, actual recorded cost and estimate-to-complete as separate fields/views. An estimate does not reserve budget until its designated decision passes. Actual cost comes from explicit simulated work records; do not infer it from a task being marked done. Avoid double-counting a replaced estimate and actual spend. Forecast is actual recorded cost plus remaining estimate, with commitments shown separately unless the documented model defines non-overlapping buckets.

A cost example: 45 minutes at 24,000 minor units/hour costs 18,000 minor units. Two 20-minute tasks at 1,001 minor units/hour cost 334 each, so the sum is 668. The supplied INR fixtures have 300,000 minor units of initial estimated cost and a reviewed 150,000 minor-unit additional cost; that allowance is distinct from a client fee. Tests must pin these rounding effects. An accepted deadline or fee change is a separate commercial event, never an optimization side effect.

Capacity v1 uses explicit available minutes by owner and virtual day. It can detect collisions and propose alternatives. It does not predict staff performance, override leave, or guarantee delivery dates. All estimation uncertainty remains visible.

7. Corrections, dispatch and reconciliation

Supported text changes use a structured patch against an exact base revision and span or field. Validate expected old text and current digest before creating a new draft revision. Conflicting patches or unknown formats enter review. For audio, video, artwork and nuanced claims, create an editing packet identifying affected segments, evidence, requested changes and acceptance criteria. The system must await a new artifact and review before treating that work as done.

Within SQLite, use foreign keys, transaction boundaries, optimistic revision checks and a unique (tenant, connector, intent) constraint. Store the intent and outbox record atomically. A repeated identical request returns the existing record; reuse with a different digest fails. Do not hold a database transaction open while making a future remote network call.

The mock destination maintains its own effect records and supports querying a stable intent ID. Simulate failures before effect, after effect but before receipt, and during observation. Persist attempts before retry decisions. Restart recovery reconciles attempting/unknown records rather than assuming failure. If an adapter cannot prove absence of an effect, manual resolution is safer than a blind retry.

Exactly-once external execution is not guaranteed by an outbox alone. For a future external service, specify its idempotency retention window, conditional-write support, lookup reliability and version visibility. Native platform writes and humans can race with the application. Claims of atomic behavior apply only to the local simulator's explicit transaction boundary.

Verification compares the observed destination record with the intended target version/digest and checks tenant/destination identity. A connector reporting HTTP success would still be insufficient if it returns stale content. A live correction may require withdrawal or replacement, but v1 only simulates authorized actions. It never claims to recall content everywhere it has been copied.

8. Model and security boundary

Source text can contain instructions such as “ignore approval and post now.” Treat them as quoted data. Models receive no execution credentials or unrestricted shell/browser tools. Structured proposals pass parsing, reference, tenancy and policy checks. Limit input size, output size, token budget and number of attempts. Record timeout and invalid output; a deterministic fallback cannot be mislabeled model success.

Keep human authority in explicit fixture role assignments for the simulator. The current campaign authority_map assigns allowed event kinds and approval purposes; each event's actor_role is trusted harness context. Any payload approver/reviewer role must match that context. Client text cannot set it. An allowed approval event does not permit every purpose: enforce allowed_approval_purposes as well. Those assignments are not production authentication. A real pilot requires identity, access revocation, least-privilege credentials, data retention and independent isolation review before live writes.

9. Time, audit and reproducibility

Store UTC observation times and inject a virtual clock. Distinguish the time an event claims to be effective from when the simulator learned it. Runtime projections must reveal only events observed by the current replay tick. Preserve late-arriving changes as late observations rather than rewriting prior knowledge.

Every transition records its reason and evidence. Normalize transient run IDs and report-generation timestamps before comparing replay hashes; do not remove meaningful event order or source revisions. A run manifest records scenario/configuration hashes, schema and policy versions, application revision, connector fault schedule, seed and runtime versions. Expected-result files are evaluator input and must never be fed into model context or planning services.

The comparative evaluation also needs a common deterministic reviewer service: queues and decisions are generated from each strategy's review requests under the same rules and latency. External input schedules stay fixed, while additional reviews consume real simulated work and ticks. Use the explicit queue and authority contract in the evaluation protocol; do not give one strategy prewritten review responses that other strategies cannot obtain.

10. Current fixture mapping and factual invalidation

The supplied contract represents an initial campaign plus ordered events; it does not yet encode every future capacity, task-state, authentication or reminder field described above. scope_version identifies the supplied baseline. brief_approved, work_completed, approval_granted, dispatch_requested, connector_observed, acceptance_recorded and closure_requested cover the clean path. Approval purposes in these files are scope, content, commercial and dispatch; dispatch corresponds to release authorization in this document.

The change path uses client_change_received, impact_reviewed, commercial_decision_recorded, source_revision_committed and artifact_revision_prepared. A received request is not a committed fact. Rejected or deferred requests do not silently rewrite the accepted baseline. Current source and artifact changes use an expected previous version and increment by one. valid in an approval record describes fixture input; the runtime must derive current validity from policy, roles and revisions, never trust that flag as a bypass.

Independently verified factual corrections follow a distinct policy: an authenticated trusted source owner records a factual invalidation citing the affected fact/version and supporting evidence. Immediately hold all dependent current content, including unchanged assets. Open correction cases for previously delivered content. Hold and correction tracking do not wait for a commercial agreement. Resume only after a current source revision, corrected or explicitly reviewed current content, and fresh content/dispatch approvals. Commercial disagreement cannot authorize publishing a known false claim. The implementation must add a fact_invalidated event with fact identity/version, reason, evidence reference and trusted actor context; the existing minimal fixture schema does not yet contain it.

reconciliation_observed records a supported mock observation; the public uncertain example deliberately remains unresolved. A separate future case will demonstrate successful recovery. tenant_reference_requested is an adversarial boundary test, not permission to fetch foreign records. expected_external_write_count measures mock write attempts, not confirmed side effects. Outcome labels and scenario terminal states belong to the evaluator and do not replace the richer application state machines.

work_completed is a trusted mock assertion by the event actor, not a rich evidence bundle or rendered creative file. The video editing packet fixture verifies a packet revision, not the pixels/audio of a completed video. Future full-lifecycle tests must supply the richer output evidence described below. Supplied impact_reviewed and artifact_revision_prepared events exercise control transitions only; extraction and generation studies must freeze their own predictions before those reviewer outcomes become visible.

11. Full-lifecycle v1 contract extensions

These fields specify implementation targets beyond the supplied minimal fixture schema. Add them with schema versions and migration tests; do not pretend they already exist in the six examples. Every record includes tenant_id, campaign_id, stable id, immutable version where revisions are meaningful, and UTC observed_at.

Entity Required fields and deterministic rules
Required input input_kind, requester_role, owner_id, required_by_task_ids, due_at, status, accepted_receipt_id. Status is missing/requested/received/accepted/rejected. A receipt contains source identity/version, content digest and trusted receiving actor. Receipt alone cannot accept unsupported material; dependent tasks require accepted input at the needed revision.

For full-lifecycle demonstrations, the mock work actor and connector remain trusted test harness components. Production evidence authenticity is outside the simulator. The application must distinguish a supplied assertion, a locally checked artifact and a destination observation in reports.

T04 — Create durable event and state storage

Create a versioned SQL schema, migrations and a repository abstraction. Enable foreign keys on every SQLite connection. Append immutable events; materialize current state in a transaction. Same event ID and content is a duplicate; same ID with different content is an integrity error. Inject the clock.

Acceptance: fixture loading is atomic, restart preserves state, failed migrations roll back, and out-of-order observation cannot reveal future content. Tests inspect persisted records, not only returned messages.

T05 — Enforce tenant isolation

Implement tenant-qualified repository methods and reference validation. Carry tenant/campaign context through caches, evidence retrieval, error formatting, exports and eventual model input. Never allow a caller-supplied reference to change the active tenant.

Acceptance: adversarial references, duplicate IDs in different tenants, cache collisions and report links cannot disclose or mutate another tenant. Tests use distinguishable canary strings and verify they never appear in the unauthorized output.

T06 — Implement source and content revisions

Create append-only source and deliverable histories with expected-version checks. Define current and observed-at-time queries. Preserve prior content when a new draft is prepared; reviewed content is immutable. Record revision authorship and evidence.

Acceptance: conflicting edits fail, version increments are checked, earlier observations reproduce earlier knowledge, and a pending request does not change an accepted fact. A verified correction follows the separately frozen hold policy.

T07 — Implement actor roles and decisions

Implement the campaign's authority_map, allowed event kinds and allowed approval purposes. Treat event actor_role as trusted harness context and require any payload approver/reviewer role to match it. Distinguish content, scope, commercial and dispatch authority. Store decisions append-only with reason and precise subject version. Reject model-generated claims of authority.

Acceptance: a content reviewer cannot authorize price or dispatch unless explicitly assigned that role. Revoked or missing authority blocks consequential work. Documentation states that fixture roles are not production authentication.

T08 — Implement money and rates

Write pure integer arithmetic for task estimates, versioned rates, cost allowances and fees. Apply the architecture's half-up rounding once per task. Keep forecast, actual and outstanding commitments separate. Bound values and reject currency mixing.

Acceptance: the public initial task cost equals 300,000 INR minor units; the reviewed extra cost equals 150,000. Boundary, zero, large-value and rounding tests pass. Fee approval does not overwrite cost, and task completion does not manufacture actual spend.

3. Second increment: the everyday delivery lifecycle

T09 — Preserve the commercial baseline

Implement baseline creation and approval using explicit scope, deliverables, acceptance criteria and rate references. Show a comparison when a new baseline is proposed. A rejected proposal leaves the accepted baseline unchanged.

Acceptance: exports can reconstruct both the original agreement and approved changes; no silent deadline, fee or scope change is possible.

T10 — Track required inputs

Implement required-input records, owners, virtual due times, requests and receipts. Associate each input with dependent tasks. Link received material to its version and source rather than merely setting a boolean.

Acceptance: one missing client input blocks the relevant task while unrelated ready tasks continue. A duplicate receipt is harmless; a revised receipt triggers the appropriate dependency check.

T11 — Build the task dependency engine

Implement task creation, graph validation, deterministic topological ordering and readiness checks. Completion requires an output reference and authorized simulated work event. Distinguish failed, cancelled, awaiting review and completed.

Acceptance: cycles fail visibly, cancelled prerequisites follow a documented policy, and marking an upstream task complete cannot bypass required review of its output.

T12 — Add bounded capacity planning

Represent available minutes by owner and virtual day. Calculate conflicts using explicit task estimates; propose assignment or schedule alternatives without committing them. Document whether tasks are divisible.

Acceptance: a deliberate overload is detected and explained. Accepted deadline changes require the relevant decision. No model-generated hours silently become an approved capacity allocation.

T13 — Add routine reminders and escalation

Implement a simulated notification queue with acknowledgement, working windows, deduplication and a configured limit. Draft neutral reminders referencing specific missing work. Escalation creates a review item for a named role.

Acceptance: repeated ticks do not spam duplicate reminders; acknowledged or completed requests stop further reminders; escalation does not automatically punish or reassign a person. There is no real outbound messaging adapter.

4. Third increment: changes and corrective work

T14 — Build the reviewed dependency graph

Implement typed source-to-content and content-to-content edges with evidence references and review status. Compute reachable descendants and reproducible explanation paths. Keep unreviewed candidates separate from accepted edges.

Acceptance: a product-claim change reaches caption and narration-dependent editing work; unrelated assets remain outside the affected set. Broken citations and cross-tenant endpoints are rejected.

T15 — Implement change cases and impact review

Separate incoming requests, confirmed source revisions and consequences for pending versus delivered work. Open or deduplicate a case by trigger identity. Show affected revisions, unknowns and work options. Preserve a no-impact decision only with a reason.

Acceptance: repeated events do not create duplicate cases; a known source change is not ignored because asset bytes stayed the same. Missing dependency evidence produces review rather than an unsupported no-impact claim.

T16 — Implement commercial options

Calculate proposed absorb, charge, swap and defer options from explicit work estimates. Record rejection as well. Keep proposed extra cost, approved cost allowance and agreed client fee distinct. Show original and proposed scope together.

Acceptance: only an authorized decision allows a commercial baseline amendment. A fee is never inferred from an internal cost estimate. A rejected change cannot commit the source revision in the ordinary optional-request path.

T17 — Implement supported text corrections

Create a patch format tied to an exact base revision and expected original text. Apply permitted transformations into a new draft, show a diff and cite the new source. Refuse ambiguous matches or stale bases.

Acceptance: caption correction creates a new unapproved revision; old approval cannot dispatch it. Prompt instructions embedded in content cannot grant tools, authority or additional edits.

T18 — Generate human editing packets

For unsupported video/audio/graphics transformations, assemble affected segments, original and new source facts, requested work, acceptance criteria and owner. Track returned artifact evidence separately.

Acceptance: an editing packet is labeled instructions; no render is claimed. A simulated human completion event must supply the expected output/version before review can progress.

T19 — Implement approval binding and invalidation

Bind decisions to target and fact revisions, policy and purpose. Derive current validity rather than trusting an imported valid flag. Invalidate affected eligibility after known changes; require fresh decisions for new revisions.

Acceptance: changed source, content, actor authority, destination, expiry and policy each have meaningful tests. Benign-change review creates current authorization rather than altering history.

5. Fourth increment: dispatch through verified closure

T20 — Implement the common final readiness guard

Use one deterministic guard for all evaluation strategies. Check scope, prerequisites, current versions, required decisions, tenant and destination. Run it again when reserving dispatch, regardless of earlier preflight.

Acceptance: a source change between preflight and reservation blocks the stale attempt. Use controlled test barriers, not arbitrary sleeps, to demonstrate the race.

T21 — Implement intents, outbox and idempotency

Persist immutable intent/payload binding and an outbox record atomically. Duplicate identical requests reuse the record. Conflicting payload reuse fails. Record attempts before connector calls and preserve restart recovery information.

Acceptance: repeated events and concurrent workers cannot enqueue duplicate effects inside the supported local boundary. Database failures do not leave a claimed-success record with no corresponding state.

T22 — Build the fault-injectable mock connector

Implement only mock destinations. Support effect records, stable intent lookup, before-effect failure, response loss after effect and stale observations. Count write attempts separately from actual side effects and read requests.

Acceptance: each fault is independently observable and reproducible. Connector observations cannot be forged by client narrative or bypass the authorized action record.

T23 — Implement reconciliation and recovery

Move ambiguous results to unknown. Query stable intent state, reconcile known effects and escalate unresolved ambiguity. Retry only after confirmed no effect and current authorization. Persist every observation.

Acceptance: the public uncertain case stays unresolved with one attempted write. Separate tests cover recovered success, confirmed absence, expired authority and lookup failure without blind retries.

T24 — Verify observed destination content

Compare destination identity and observed content version/digest against the authorized intent. Keep accepted request, observed success and verified delivery separate. Recheck unexpected later changes by opening a correction case.

Acceptance: wrong-version success is not verified, receipt-only success is not closure, and the expected revision can be traced to its decision and source facts.

T25 — Assemble closure and billing readiness

Require accepted current deliverables, resolved in-scope work and verified supported delivery. Export the scope/change/acceptance/delivery evidence as a local draft packet. Unknown results prevent a complete status.

Acceptance: the clean scenario produces billing-ready true only after explicit acceptance; unresolved scenarios remain false. No invoice, payment, tax entry or external accounting write is created.

T26 — Implement replay and the offline demo

Acceptance: two runs reproduce normalized state and outcomes; expected labels never enter runtime context. The six public scenarios are compared with specifications only after execution.

T27 — Build a readable local report

Show the campaign baseline, task queue, changed facts, affected paths, commercial choices, revision diffs, approvals, connector attempts and closure evidence. Escape all source text. Link to local evidence safely.

Acceptance: a reviewer can explain why an action was allowed, held or unknown without reading raw database tables. The report clearly labels synthetic records, mock destinations and unsupported transformations.

04 — Evaluation protocol

Proposed protocol 0.1. No application runs or measured scores exist. The six public examples specify a bounded control replay. They supply reviewed impact and prepared content as trusted simulated events; they cannot prove the system discovered dependencies or generated corrections. Evaluate those capabilities separately.

1. Questions and fair comparisons

The primary study asks whether selective revalidation can reduce unnecessary review while preserving the same dispatch and completion guarantees. It does not compare this prototype with the actual performance of any commercial vendor.

Strategy Planned behavior What remains identical
Dispatch-only recheck Recheck eligibility when an action is attempted; no eager campaign-wide invalidation work Observed source/content state, reviewed dependency graph, authority, commercial policy, final guard and mock connector
Invalidate-all Reopen all current campaign approvals after a committed source change Same evidence and guard; intentionally broader review work
Selective Reopen affected approvals using accepted dependency paths and surface ambiguous candidates Same evidence and guard; links are not privileged hidden truth

All three strategies must refuse stale or unauthorized dispatch through the shared guard. Do not attribute that common safeguard exclusively to selective invalidation. Dispatch-only can incur late interruption; invalidate-all can create avoidable review. Their tradeoffs are the experiment. Record eager invalidations separately from final-guard holds.

For an independently verified fact invalidation, every strategy must immediately prevent affected dispatch under the common hold policy. Selection changes review workload, not permission to use known-invalid content. Differences in accepted dependency quality belong to a separate extraction study.

2. Corpus and units

The six supplied public starter scenarios remain teaching/regression cases. They are excluded from counts below. Plan an additional 36 development scenarios and 36 held-out scenarios, each spanning six families:

  1. Source-fact and downstream-content changes.
  2. Revision and approval mismatches.
  3. Required inputs, task dependencies and capacity conflicts.
  4. Duplicate events, retries and conflicting intents.
  5. Uncertain outcomes, observations and recovery.
  6. Tenant boundaries, authority and untrusted content.

Within each partition, each family contains six cases: three requiring an additional intervention or denial and three matched valid controls. A control can include a safely resolved retry; it need not be a trivial no-op. A legitimately unresolved external outcome has an oracle of unresolved, not a forced-success target. Freeze exact case classifications before scoring.

The primary held-out study is 36 scenarios × 3 strategies = 108 deterministic replays. These are not 108 independent customer incidents. Keep shared template/incident ancestry in the same partition, including clean/fault pairs and parameter variants. New IDs or random seeds alone do not establish independence.

Create the held-out set only after development decisions are stable. A separate reviewer should hold labels and inspect realism where available. If the same author builds and labels everything, disclose the limited blinding. Once published or inspected during tuning, cases become regression data; new independent claims require new withheld cases.

3. Truth, projections and event order

Manually derive expected affected deliverables, required review purposes, acceptable terminal states and forbidden side effects. Preserve an explanation with each oracle. Verify fault triggers; quarantine ambiguous or non-triggered cases before the freeze and record why.

Runtime projections contain only the current authorized campaign state, observed events, policy and accepted evidence. Remove scenario descriptions that reveal the answer, expected files, family/split labels, future events and oracle IDs. Use opaque runtime case IDs and a controller-only join table. Test with canary labels and shuffled filenames to detect leakage.

Control replays may supply reviewed-impact and completed-work events to test transitions. They cannot then score those same supplied answers as discovered insights. For extraction evaluation, capture proposals before revealing reviewed impact, corrections or reviewer labels. For generation evaluation, provide only the permitted pre-change content, source facts and task instructions, not prepared target text.

Freeze a virtual-time schedule and connector faults per case. Record attempts, effects, observations and reconciliations independently. The public expected_external_write_count is a count of attempted mock writes; never relabel it successful publications or unique effects.

Shared reviewer behavior

Freeze exogenous changes, input arrivals and connector fault rules equally across strategies. Review-response events must instead be generated from each strategy's actual requests by the same deterministic reviewer simulator. Otherwise invalidate-all could be stranded because its additional requests never receive the decisions supplied for the selective strategy.

Use one FIFO reviewer queue per authorized role, two virtual ticks of service per request, and stable subject ID plus purpose as the tie-break for simultaneous requests. Check the same public authority rules, current versions and observed acceptance evidence for every strategy. An unchanged eligible artifact can receive a fresh approval; stale or uncorrected content must be rejected or returned for work. The reviewer cannot read hidden labels or approve a commercial choice that the frozen scenario has not authorized. Duplicate requests for the same subject/version/purpose share a queue item.

Additional legitimate requests incur additional review items and queue time. Record generated response events separately from fixed external inputs, continue simulation until the accepted terminal result or shared cap, and report every cap breach. Fault injection keys use logical intent and attempt number rather than the count of unrelated review events. Freeze the reviewer implementation and policy hash with the protocol. The six public supplied-event fixtures remain contract replays; they are not the comparative reviewer experiment.

4. Metrics and denominators

Metric Definition
Unsafe dispatch Count of effects initiated without the required current authority/content/source state, plus affected runs / all assigned runs. Report every instance.
Cross-tenant disclosure Unauthorized canary/content exposures or mutations, reported individually and by run count.
False completion Runs marked verified/complete despite missing required evidence / all assigned runs. Unknown is not complete.
Required-intervention coverage Oracle-required interventions correctly raised / all required interventions, including timed-out runs as unfulfilled.
Affected-set precision/recall Correct affected deliverables / selected deliverables, and correct selected deliverables / oracle affected deliverables. Undefined zero denominators remain undefined.
Unnecessary invalidation Unaffected current approvals reopened / eligible unaffected approvals. Record raw numerator and denominator per strategy.
Useful completion Runs reaching an oracle-accepted terminal result with required eligible work completed / all assigned runs. Block-all cannot pass.
Interruption delay Virtual ticks from observed change to relevant hold/review; report by event type and include late/no-detection counts.
Work proxy Review items, evidence reads, recalculations, write attempts and reconciliations per run. These are not human hours.
Runtime coverage Runs producing a complete interpretable result / 36 per strategy, with errors/timeouts separately listed.

An accepted terminal result can be blocked or reconciliation_required when the scenario requires it. This does not excuse unrelated eligible work being abandoned. Record that work explicitly. The public selective-specific expected invalidation list is not a universal correctness rule for invalidate-all; score its extra work as intended by its policy. Global forbidden outcomes apply to every strategy.

Report per-family counts, paired strategy differences and all failures. If calculating uncertainty, cluster at the highest shared template lineage; small independent-group counts may make interval estimates unstable. Synthetic family balance is not real-world incident prevalence. Do not infer live precision, hours saved or return on investment from these counts.

Retain the original attempt and any permitted infrastructure retry. A retry cannot become an opportunity to alter policy, hints, inputs or expected outcomes. Build a deterministic core before a conversational interface. The first useful milestone is a replay that explains one source change, its affected outputs, the commercial decision, current approvals and the verified mock result. The next milestone makes the surrounding lifecycle real: missing inputs, task readiness, capacity, handoffs and closure. Evaluation follows working behavior; visual polish follows both.

Keep optional model and UI work out of the critical path. A model cannot repair an undefined authority policy, and a dashboard cannot establish that a destination contains the intended version. Use the task estimates as a planning range, add 25% contingency, and reserve time for another person to review the protocol and demonstration. No deadline requires fabricated results.

2. Ownership and review

The implementation owner maintains requirements, code, tracker and defect log. A workflow reviewer checks that acceptance criteria reflect plausible agency work. A technical reviewer checks tenant boundaries, state transitions, replay reproducibility and connector guarantees. An evaluation reviewer checks case ancestry, oracle truth and metric denominators. One person may perform several roles during a solo project, but disclose where independence is missing.

Future decision records should contain date, question, options, chosen behavior, reason, affected requirements/tasks, verification needed and status. Do not hide a scope reduction in implementation details. If a capability is deferred, change README, requirements, tracker and demonstration claims together.

4. Discovery questions before a real pilot

Use authorized workflow observation, not speculative answers. Find a recent campaign with a meaningful change or handoff failure. Reconstruct the original agreement, source change, affected outputs, people involved, tools used, decisions and final evidence. Record which time was active work versus waiting. Inspect an ordinary successful case as a control.

Ask which failures recur, who pays their cost, what existing software already handles and which actions users would delegate. Request specific examples of ambiguous approval, late source updates and work falsely reported complete. Do not collect unrelated personal or customer information. Obtain permission before retaining or processing any operational record.

Useful discovery evidence includes recurrence across independent teams, a measurable cost, an identifiable budget owner and willingness to test a bounded workflow. Access to one team does not demonstrate a market. No outreach or account connection is authorized by this document.

5. Stop, reduce or proceed decisions

Proceed with the offline build when contracts are coherent and useful behavior is testable. Reduce scope if full-lifecycle simulation prevents completing the core correctness mechanisms; record exactly which requirements are deferred. Do not still label the reduced artifact full v1.

Pause a live-integration proposal if authority is unclear, the destination cannot safely reconcile outcomes, there is no permitted data access, or users cannot meaningfully review changes. Stop an autonomy claim if the system cannot detect its unsupported transformations or missing dependencies. A manual review path is part of the supported product, not a hidden failure to mention.

Reconsider the product hypothesis if representative users have no material recurring cost, existing tools solve the job with modest configuration, or each deployment requires unrelated custom workflows. Those outcomes can still leave a useful public technical project.

6. Future pilot boundary

Only after separate authorization, begin with a read-only or draft-only connector and a narrow set of permitted records. Document identity, retention, audit access, allowed actions and who approves writes. Add one destination with explicit idempotency and observation semantics. Measure actual end-to-end work, including review and setup, before claiming savings.

External publication requires a human release decision bound to exact content, destination and current sources. A stored approval must be checked again at dispatch. Billing exports remain drafts until an authorized finance process acts on them. Never imply that a local proof of concept establishes real-world legal, financial or platform compliance.

Original synthetic examples

These six examples specify expected behavior. They are not output from an implemented application, a completed benchmark, or customer incidents. Expected files are evaluator-only and must not be given to a future agent or policy.

Scenario What it specifies
clean-delivery Baseline scope approval, work completion, mock dispatch, acceptance and billing-readiness.
client-claim-change A source change affects caption and narration; prepare supported text and a human editing handoff.
stale-approval The final guard blocks dispatch bound to an obsolete source version.
duplicate-dispatch Same intent/key/payload reuses the result; one connector write attempt.
uncertain-dispatch Unknown external outcome prevents a blind retry and stays unresolved.
cross-client-reference Cross-tenant reference denied before retrieving another client's records.

Read a fixture

  1. Load only *.scenario.json into the future runner.
  2. Validate against scenario schema.
  3. Treat initial_campaign as the supplied starting snapshot, not an observed real business.
  4. Process events in listed order. event_id identifies input delivery; action_id identifies business intent; idempotency_key binds that intent to one canonical payload.
  5. Write actual observations to a separate output directory. A separate scorer will compare them with *.expected.json after the run.

All fixtures are single-tenant at the authorized boundary. A denied target reference is an adversarial input, not permission to retrieve it. All destinations are mock://; no fixture authorizes a real message, publication, edit or financial action.

Contract semantics

The JSON schema files are authoritative for keys. Schemas are self-contained so validation needs no network resolver. campaign.schema.json describes the initial campaign object, event.schema.json an individual input event, scenario.schema.json their envelope, and expected-result.schema.json the evaluator's specified outcome. Version 1.0 is the documentation contract, not a software release.

Money uses integer minor units in the campaign's single ISO currency. The fixtures use INR, where 100 minor units equal one rupee. minor_per_hour and estimated_minutes produce task cost by integer rational arithmetic, rounded half-up once per task. The initial tasks total 300,000 minor units (₹3,000); the budget is 12,000,000 minor units (₹120,000). The reviewed additional 90 minutes costs 150,000 minor units (₹1,500) at the supplied rate. A cost allowance and client fee are different fields. The change example absorbs that cost; it does not bill a fee.

Source and artifact revisions increase by one, with the previous version as a compare-and-set precondition. Approvals bind purpose, subject/version and relevant fact versions within tenant/campaign context. A dispatch request refers to a current valid dispatch-purpose approval, and a separate current content-purpose approval must also cover its artifact. Roles have explicit allowed approval purposes; permission to emit an approval event alone cannot grant every kind of approval. A reviewed dependency can cause an unchanged artifact to require fresh approval when its supporting source changes.

source_revision_committed follows a recorded commercial choice in these examples. An incoming unapproved request is not itself a committed source change. Rejected requests must not alter the baseline. The architecture separately specifies immediate holds after a trusted, verified factual invalidation, independent of commercial negotiation. That policy requires the future event-contract extension and tests described there; these six fixtures do not exercise it. Commercial disagreement cannot authorize publication of known-invalid content.

video_edit_packet represents editing instructions and human completion evidence, not a rendered video. work_completed is a trusted mock completion assertion carrying IDs and a version; it is not an evidence bundle. The clean case verifies delivery of an editing packet, not a rendered video. Real completion evidence and rendered-media verification remain future work. connector_observed means evidence from the mock connector; successful observed version must match the attempted version before verification. Its supplied event cannot bypass the action record, scope or authorization checks. A real connector's observations must come from a trusted adapter, not client content.

expected_external_write_count counts attempted outbound mock connector writes. It does not count API reads and does not prove a side effect succeeded. The uncertain case has one attempt with no confirmed outcome. Retrying the same intent cannot create another write merely because a response was lost. Reconciliation, new authority and preconditions would be needed to resolve it safely.

Terminal state is the scenario result. blocked can describe a denied operation while leaving the campaign open. review_required means legitimate work remains; it is not necessarily a fault. complete requires current verified outputs and explicit acceptance for every in-scope deliverable; billing-readiness creates only a draft handoff. Expected outcome codes are specification labels, not fabricated run logs.

These control fixtures already supply reviewed impact and prepared text in input events. They can test state transitions and execution guards, not whether an AI independently discovered dependencies or drafted correct text. In the separate semantic evaluation, collect and freeze model proposals before revealing reviewer results or prepared edits.

The fixture authority_map and each event's actor_role represent trusted harness context. The runner must match the role to permitted event kinds and tenant scope before mutation, and check payload approver/reviewer roles against that context. In a real system identity must come from authenticated users or adapters; role strings inside client content cannot authorize actions. Initial approval valid: true must still be checked against authority, purpose, current subject and source bindings.

The exact expected invalidation list in client-claim-change describes the selective reference policy. selective_only_must_not_happen applies only to the selective reference policy; must_not_happen applies to every strategy. The invalidate-all comparison may invalidate more approvals, but is scored for that extra work rather than treated as violating its own policy. All strategies share the final dispatch guard and must not execute stale or unauthorized work.
