# 07 — Delivery decisions and risks

This is a proposed delivery plan. No customer interviews, production access, measured savings or product adoption are claimed. Use the [task tracker](../planning/tasks.csv) for implementation status and replace estimates with actual evidence as work proceeds.

## 1. Build order and investment of effort

Build a deterministic core before a conversational interface. The first useful milestone is a replay that explains one source change, its affected outputs, the commercial decision, current approvals and the verified mock result. The next milestone makes the surrounding lifecycle real: missing inputs, task readiness, capacity, handoffs and closure. Evaluation follows working behavior; visual polish follows both.

Keep optional model and UI work out of the critical path. A model cannot repair an undefined authority policy, and a dashboard cannot establish that a destination contains the intended version. Use the task estimates as a planning range, add 25% contingency, and reserve time for another person to review the protocol and demonstration. No deadline requires fabricated results.

## 2. Ownership and review

The implementation owner maintains requirements, code, tracker and defect log. A workflow reviewer checks that acceptance criteria reflect plausible agency work. A technical reviewer checks tenant boundaries, state transitions, replay reproducibility and connector guarantees. An evaluation reviewer checks case ancestry, oracle truth and metric denominators. One person may perform several roles during a solo project, but disclose where independence is missing.

Future decision records should contain date, question, options, chosen behavior, reason, affected requirements/tasks, verification needed and status. Do not hide a scope reduction in implementation details. If a capability is deferred, change README, requirements, tracker and demonstration claims together.

## 3. Main risks and response

| Risk | Early signal | Required response |
|---|---|---|
| Scope becomes a universal ERP | New accounting, payroll, inventory or tax modules enter the critical path | Keep billing as a draft evidence export; define separate integration scope later. |
| Existing tools already solve the proposed job | A configured incumbent completes representative cases adequately | Record that evidence; focus the repository on engineering/evaluation value rather than unsupported uniqueness. |
| Dependency extraction misses important content | An affected narration or disclaimer is absent from proposed links | Surface uncertainty, require reviewed links, measure recall separately and avoid autonomous release claims. |
| Unnecessary rework overwhelms reviewers | Most proposed impacts are unrelated or already resolved | Measure false invalidations and useful completion; refine on development data only. |
| Commercial approval becomes implicit | An estimated cost is treated as a client fee or a requested date becomes promised | Separate cost/fee/authority records and reject unauthorized changes. |
| Incorrect approval survives a revision | Old source or content references still authorize dispatch | Enforce the common final guard and preserve a regression test for every discovered path. |
| False external success | A timeout or accepted request is shown as complete | Track unknown outcomes and require destination observation; expose unresolved cases. |
| Duplicate effect after recovery | Restart or retry emits the same action twice | Persist intent binding and reconcile before retry; document adapter limitations. |
| Client data crosses boundaries | A foreign canary appears in context, reports or errors | Treat as a critical defect; stop external use and fix all retrieval/cache/export paths. |
| Prompt injection changes behavior | Source content requests authority, secrets or execution | Keep text as data, constrain proposals and never grant execution tools to extraction. |
| Creative capability is overstated | An editing packet is labeled as a rendered correction | Separate supported text patches, human work and verified artifact evidence. |
| Benchmark overfitting | The same templates appear in development and held-out cases | Freeze lineage splits; disclose contamination and author a new withheld set. |
| “AI” means supplied answers | Reviewed impact or prepared target text is counted as model output | Separate control replay from semantic extraction/generation and freeze predictions first. |

## 4. Discovery questions before a real pilot

Use authorized workflow observation, not speculative answers. Find a recent campaign with a meaningful change or handoff failure. Reconstruct the original agreement, source change, affected outputs, people involved, tools used, decisions and final evidence. Record which time was active work versus waiting. Inspect an ordinary successful case as a control.

Ask which failures recur, who pays their cost, what existing software already handles and which actions users would delegate. Request specific examples of ambiguous approval, late source updates and work falsely reported complete. Do not collect unrelated personal or customer information. Obtain permission before retaining or processing any operational record.

Useful discovery evidence includes recurrence across independent teams, a measurable cost, an identifiable budget owner and willingness to test a bounded workflow. Access to one team does not demonstrate a market. No outreach or account connection is authorized by this document.

## 5. Stop, reduce or proceed decisions

Proceed with the offline build when contracts are coherent and useful behavior is testable. Reduce scope if full-lifecycle simulation prevents completing the core correctness mechanisms; record exactly which requirements are deferred. Do not still label the reduced artifact full v1.

Pause a live-integration proposal if authority is unclear, the destination cannot safely reconcile outcomes, there is no permitted data access, or users cannot meaningfully review changes. Stop an autonomy claim if the system cannot detect its unsupported transformations or missing dependencies. A manual review path is part of the supported product, not a hidden failure to mention.

Reconsider the product hypothesis if representative users have no material recurring cost, existing tools solve the job with modest configuration, or each deployment requires unrelated custom workflows. Those outcomes can still leave a useful public technical project.

## 6. Future pilot boundary

Only after separate authorization, begin with a read-only or draft-only connector and a narrow set of permitted records. Document identity, retention, audit access, allowed actions and who approves writes. Add one destination with explicit idempotency and observation semantics. Measure actual end-to-end work, including review and setup, before claiming savings.

External publication requires a human release decision bound to exact content, destination and current sources. A stored approval must be checked again at dispatch. Billing exports remain drafts until an authorized finance process acts on them. Never imply that a local proof of concept establishes real-world legal, financial or platform compliance.
